# Phase 07.4.04 — Idempotency and Result Caching Specification

## 1. Overview
Virtual Try-On inference is computationally intensive and incurs direct external provider API costs (\$0.025 to \$0.06 per generation). Network flakiness, mobile app retries, and rapid double-taps by shoppers must never result in duplicate billing or redundant inference runs.

FashXStudio implements a two-tier protection model:
1. **Request Idempotency**: Prevents concurrent duplicate submissions using client idempotency keys and server canonical request hashing.
2. **Reusable Result Caching**: Reuses existing valid artifacts when an identical generation request is made, while strictly enforcing DPDP consent, takedowns, and data retention windows.

---

## 2. Canonical Request Hashing

A deterministic SHA-256 request hash is calculated for every incoming job acceptance request via `backend/fashx/tryon/idempotency.py:compute_request_hash`:

$$\text{hash} = \text{SHA-256}\Big(\text{user\_id} \mathbin{\Vert} \text{shopper\_asset\_id} \mathbin{\Vert} \text{garment\_asset\_id} \mathbin{\Vert} \text{product\_id} \mathbin{\Vert} \text{category} \mathbin{\Vert} \text{policy\_version}\Big)$$

### Sensitivity Rules
- **Asset Versioning**: If a shopper uploads a new version of their body photo, the asset ID changes, which inherently changes the request hash.
- **Merchant Image Updates**: If a merchant updates their product garment image, the garment asset ID changes, producing a new hash.
- **Validation Policy Version**: Bumping the validation policy (e.g. from `v1.0` to `v2.0`) invalidates previous cache calculations, ensuring jobs are regenerated under updated quality standards.

---

## 3. Client Idempotency Key Handling

Clients may supply an optional `Idempotency-Key` header or payload field (e.g. client UUID):
1. **Key Lookup**: The database checks for existing jobs associated with `(user_id, idempotency_key)` within the active 24-hour window.
2. **Identical Request**: If a job exists and its `request_hash` matches the current request:
   - Return the existing job with HTTP 202 Accepted and current `status`.
   - No new outbox event or queue message is dispatched.
3. **Mismatched Request**: If a job exists under the same key but with different parameters (differing `request_hash`):
   - Reject immediately with **HTTP 409 Conflict** (`idempotency_conflict`).
   - Prevents accidental key reuse across distinct try-on actions.

---

## 4. Reusable Result Caching

When a shopper requests a try-on with an identical request hash and no conflicting idempotency key, FashXStudio evaluates cache eligibility:

```
[ New Request Received ]
          |
          v
[ Calculate Canonical Hash ]
          |
          v
[ Lookup Existing COMPLETED Job by Hash ]
          |
     +----+----+
     |         |
 (Found)   (Not Found)
     |         |
     v         v
[ Eligibility Checks ]      [ Create New Job & Outbox Event ]
 1. DPDP consent active?
 2. Merchant rights active?
 3. Product not delisted?
 4. Artifact < retention TTL (e.g. 30 days)?
     |
  +--+--+
  |     |
(Pass) (Fail)
  |     |
  |     +-----> [ Invalidate Cache & Create New Job ]
  v
[ Reuse Existing Artifact ]
- Return HTTP 202 (or instant COMPLETED)
- 0 Provider Cost Incurred
```

### Invalidation Conditions (Fail-Closed)
A cached result is **ineligible** and discarded if:
1. Shopper has revoked consent for `THIRD_PARTY_VTO_PROCESSING`.
2. Merchant has revoked image rights or issued a DMCA/IP takedown for the product garment image.
3. The catalog item has been deleted, archived, or delisted.
4. The artifact file has exceeded the 30-day DPDP storage retention window or has been pruned from S3.
