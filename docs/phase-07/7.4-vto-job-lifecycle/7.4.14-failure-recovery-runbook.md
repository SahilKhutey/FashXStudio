# Phase 07.4.14 — Operational Failure Recovery Runbook

## 1. Overview
This runbook provides actionable standard operating procedures (SOPs) for the engineering and on-call team to diagnose and resolve Virtual Try-On lifecycle incidents, stuck jobs, provider outages, and lease contention.

---

## 2. Common Incident Playbooks

### Playbook A: Spike in `SUBMISSION_UNKNOWN` Jobs
- **Symptoms**: Elevated alerts on metric `vto_jobs_submission_unknown_total`. Jobs accumulating in `SUBMISSION_UNKNOWN` status.
- **Root Cause**: Upstream provider POST endpoint experiences high packet loss, DNS flapping, or HTTP 504 timeouts.
- **Triage Steps**:
  1. Inspect provider status page (e.g. `status.fashn.ai`).
  2. Query database for recent attempts:
     ```sql
     SELECT id, job_id, provider, started_at, error_details 
     FROM tryon_provider_attempts 
     WHERE status = 'UNKNOWN' AND created_at > NOW() - INTERVAL '1 hour';
     ```
  3. Execute reconciliation task:
     ```bash
     python -m fashx.workers.reconciliation --reconcile-unknown-submissions
     ```
  4. The reconciliation worker queries the provider by idempotency key. If the provider did not receive the job, the job is cleanly cancelled or re-queued.

---

### Playbook B: Stuck Jobs with Expired Leases (`PROCESSING`)
- **Symptoms**: Jobs remain in `PROCESSING` longer than 180 seconds; mobile users report indefinite spinning.
- **Root Cause**: Worker pod terminated ungracefully (Kubernetes OOMKilled or spot instance eviction).
- **Triage Steps**:
  1. Verify lease expiration:
     ```sql
     SELECT id, locked_by, lock_expires_at, updated_at 
     FROM tryon_jobs 
     WHERE status = 'PROCESSING' AND lock_expires_at < NOW();
     ```
  2. The automated recovery sweeper runs every 60 seconds:
     ```sql
     UPDATE tryon_jobs 
     SET status = 'QUEUED', locked_by = NULL, lock_expires_at = NULL 
     WHERE status = 'PROCESSING' AND lock_expires_at < NOW() AND attempts < 3;
     ```
  3. If attempts $\ge 3$, transition directly to `FAILED` with error code `worker_lease_expired`.

---

### Playbook C: Provider Outage or Rate Limit Flapping
- **Symptoms**: Burst of `503 Service Unavailable` or `429 Too Many Requests` from provider adapter.
- **Triage Steps**:
  1. Check concurrency controller pool status.
  2. If provider is degraded, temporarily pause outbox publishing:
     ```bash
     aws ssm put-parameter --name /fashx/staging/tryon/circuit_breaker --value "OPEN" --overwrite
     ```
  3. Jobs remain safely durable in `tryon_jobs` table in `QUEUED` state until upstream recovers.
  4. Once upstream is restored, resume outbox publishing without loss of customer requests.
