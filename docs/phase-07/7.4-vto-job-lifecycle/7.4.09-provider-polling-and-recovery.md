# Phase 07.4.09 — Provider Polling, Webhooks, and Crash Recovery

## 1. Overview
External VTO inference engines (such as FASHN v1.6) run asynchronously on GPU clusters, taking between 5 and 30 seconds to generate high-resolution try-on outputs. FashXStudio supports both **Bounded Polling with Jitter** and **Webhook Notifications**, backed by resilient crash recovery.

---

## 2. Bounded Polling Algorithm

When operating in polling mode:
1. **Initial Delay**: Worker waits 2.0 seconds after successful submission before initiating the first status poll.
2. **Backoff Schedule**: Subsequent polls use an incremental interval with random jitter:
   $$t_{\text{poll}} = \min(t_{\text{prev}} \times 1.25 + \text{jitter}(0, 0.5), 5.0\text{ s})$$
3. **Hard Polling Deadline**: The maximum polling duration is capped by configuration (default: 180 seconds).
4. **Transient Error Resilience**: If a status poll returns a transient network failure (e.g. HTTP 502 or connection timeout), the worker retries up to 3 times before failing the job, preventing temporary network blips from discarding in-flight inference.

---

## 3. Webhook Architecture (Optional Inbound Signal)

In high-volume environments, providers may notify FashXStudio via an inbound webhook:
- **Webhook Endpoint**: `POST /api/v1/tryon/webhooks/{provider}`
- **Verification**: Signature verification via HMAC-SHA256 (`X-Provider-Signature`) using secret stored in AWS Secrets Manager.
- **Action**: On receipt of a valid completion webhook, the webhook handler updates `tryon_jobs.progress_stage = "DOWNLOADING_OUTPUT"` and signals the worker via Celery/Redis pub-sub.

---

## 4. Crash & Restart Recovery

If a worker container crashes or restarts while a job is in `SUBMITTED` status:
1. **Durable Provider ID**: Because `provider_job_id` is committed to PostgreSQL immediately upon submission return, the new worker reading the job recovers `provider_job_id`.
2. **Resume Polling**: The new worker skips submission entirely and resumes polling directly:
   ```python
   if job.provider_job_id:
       result = await adapter.collect(job.provider_job_id)
   ```
3. **No Lost Work**: Jobs do not get abandoned or restarted from scratch when worker pods are recycled.
