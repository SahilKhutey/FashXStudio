# Phase 07.4.06 — Transactional Outbox and Queue Architecture

## 1. Overview
Direct dual-writes to both PostgreSQL and a message broker (RabbitMQ/SQS/Celery) suffer from standard dual-write distributed failures: if the database commits but the queue publish fails, the job is orphaned; if the queue publish succeeds but the database transaction rolls back, workers process phantom jobs.

To guarantee at-least-once message delivery without distributed transactions (XA), FashXStudio utilizes the **Transactional Outbox Pattern**:
1. The API inserts `TryOnJob` and `OutboxMessageRecord` within the **same atomic database transaction**.
2. A lightweight outbox relay process polls unpublished outbox records and publishes them to the message broker.
3. Workers acknowledge messages after claiming the job via lease in PostgreSQL.

---

## 2. Outbox Schema and Event Topic

Outbox records are persisted in the existing `outbox_messages` table via `SqlOutboxRepository`:

- **Event Topic**: `vto.job.queued`
- **Partition Key**: `job_id` (guarantees ordered delivery for a given job)
- **Status Transitions**: `PENDING` $\rightarrow$ `PUBLISHED` (or `FAILED` after max retries)

### Payload Minimalism & Security
Outbox messages **never** include Personally Identifiable Information (PII), customer body photos, or presigned S3 URLs. Payloads are strictly minimal references:

```json
{
  "event_type": "vto.job.queued",
  "version": "1.0",
  "job_id": "9fa85f64-5717-4562-b3fc-2c963f66afa9",
  "user_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "timestamp": "2026-11-24T09:40:00Z"
}
```

The worker uses `job_id` to query PostgreSQL directly under an isolated transaction, loading fresh entity state.

---

## 3. Worker Queue Processing & Deduplication

Because message brokers guarantee **at-least-once** delivery, the same message may arrive multiple times (e.g. broker retry, worker restart, network blip).

The worker eliminates duplicate execution using atomic database claiming:
1. When worker receives `job_id`, it executes:
   ```python
   job = await uow.jobs.claim_job(job_id=job_id, worker_id=self.worker_id, lease_seconds=120)
   ```
2. If the job is already `COMPLETED`, `FAILED`, or claimed by an active worker whose lease has not expired:
   - `claim_job` returns `None`.
   - The worker immediately acknowledges the message and exits without performing inference or calling the external provider.
3. If the lease is expired (zombie worker), the new worker re-claims the job, updates `locked_by`, extends `lock_expires_at`, and resumes from the durable state.
