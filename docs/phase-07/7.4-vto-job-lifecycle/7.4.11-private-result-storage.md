# Phase 07.4.11 — Private Result Storage Architecture

## 1. Overview
Virtual Try-On result images contain synthetic representations of customer bodies paired with commercial garments. These images constitute sensitive personal data under India's Digital Personal Data Protection (DPDP) Act. They must **never** be stored in public S3 buckets, exposed over static unauthenticated URLs, or retained without clear lifecycle policies.

---

## 2. Storage Key Convention and Isolation

Result images are stored exclusively in private S3 buckets (e.g. `fashx-results-staging`, `fashx-results-prod`) using server-generated deterministic keys:

$$\text{s3\_key} = \texttt{tryon-results/}\{\text{job\_id}\}\texttt{.jpg}$$

### Storage Characteristics
- **No Public Read**: The S3 bucket has AWS S3 Block Public Access enabled at the account and bucket level.
- **Server-Side Encryption**: Encrypted at rest via AWS KMS (`aws:kms`) using customer-managed keys.
- **No User Input in Path**: Keys are constructed solely from verified UUIDs; user names, filenames, or directory structures are forbidden to eliminate path traversal vulnerabilities.

---

## 3. Write-Verification Protocol

To eliminate silent S3 upload failures or corrupted network writes:
1. **Multipart / Single PUT**: Uploads normalized JPEG bytes with `Content-Type: image/jpeg`.
2. **Immediate HeadObject Check**: Immediately following PUT, the storage adapter issues an S3 `HeadObject` request:
   - Verifies the object exists.
   - Verifies the returned `Content-Length` exactly matches the length of the validated bytes.
3. **Rollback & Orphan Cleanup**: If the database transaction fails after S3 PUT, an asynchronous cleanup job or outbox event deletes the uncommitted S3 object to prevent orphaned storage bloat.
