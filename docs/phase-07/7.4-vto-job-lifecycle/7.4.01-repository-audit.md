# Phase 07.4.01 — Repository and Integration Audit

## 1. Overview
Before modifying code for Phase 07.4, this audit reconciles the existing Virtual Try-On components (`CreateTryOnJobUseCase`, `SubmitTryOnJobUseCase`, `ProcessTryOnJobUseCase`, `TryOnRepository`, `TryOnAdapter`, `OutboxMessageRecord`, `S3Storage`, and Celery worker) into one unified, production-ready lifecycle.

---

## 2. Key Architecture Questions & Findings

| # | Question | Current Repository Reality | Required Phase 07.4 Hardening |
| :-: | :--- | :--- | :--- |
| 1 | **Which API route currently invokes job creation?** | `POST /api/v1/tryon/jobs` in `backend/fashx/tryon/router.py`. | Unify request acceptance into a dedicated use case returning HTTP 202 Accepted with canonical response schema. |
| 2 | **Does the route always use the authenticated principal?** | Route checked `effective_user_id = request.user_id or UUID(principal.user_id)` and raised 403 on mismatch. | Remove `user_id` from client request schema (`extra="forbid"`); derive `user_id` strictly from JWT `principal.user_id`. |
| 3 | **Does job creation invoke Phase 07.3 validation?** | Phase 07.3 validation was integrated in `ProcessTryOnJobUseCase` worker execution, but not pre-screened in `submit_tryon_job`. | Invoke combined validation during job acceptance or pre-validation, enforcing fail-closed rejection before queuing. |
| 4 | **Is third-party VTO consent checked separately from body-photo consent?** | `create_job.py` and `submit_job.py` checked `body_photo`. | Check `THIRD_PARTY_VTO_PROCESSING` with fallback to `body_photo` in accordance with DPDP consent specifications. |
| 5 | **Is the complete merchant permission evaluator used?** | Code checked `src.status != "cleared" or not src.rights_tryon`. | Enforce complete Phase 05/07.3 permission evaluation (`IMAGE_AI_PROCESS` and `VTO_PROCESS` scopes, takedown checks). |
| 6 | **Does the request transaction persist an outbox event?** | `SubmitTryOnJobUseCase` committed `job` and then invoked `dispatcher.dispatch(job.id)` as a second step. | Persist `TryOnJob` and `OutboxMessageRecord` inside the same database transaction. |
| 7 | **Does the worker resume a saved provider ID after restart?** | `process_job.py` line 402 checks `if not provider_job_id:`, but `set_provider_job` was done after `submit()`. | Persist a durable `TryOnProviderAttempt` before submitting; record `provider_job_id` immediately upon submission acceptance. |
| 8 | **Can a stale worker overwrite a job?** | `TryOnJob` tracked `locked_by`, but `update_status` did not guard on `locked_by == worker_id`. | Add `transition_if_owned` enforcing conditional updates on `(id, locked_by, status)` to prevent stale worker overwrites. |
| 9 | **Is the provider submission attempt persisted before POST?** | No attempt row existed; `TryOnJob.provider_job_id` was written after `submit()` returned. | Introduce `TryOnProviderAttempt` table; persist as `PREPARED` and `SUBMITTING` before dispatching POST to provider. |
| 10 | **Is an ambiguous submission handled without duplicate inference?** | Network timeout during `submit()` raised `TryOnError` which could trigger blind retry. | If provider POST times out or disconnects, transition attempt to `UNKNOWN` and job to `SUBMISSION_UNKNOWN`; require reconciliation before retry. |
| 11 | **Does output download validate redirects and destination hosts?** | Adapter downloaded via HTTP client without SSRF checks. | Add `validate_provider_output` and safe download boundary: HTTPS only, reject loopback/private IPs, strict byte limit (15 MB). |
| 12 | **Is the result private and owner-only?** | `GET /jobs/{job_id}` verified owner if `user_id` provided. | Add dedicated `GET /jobs/{job_id}/result` endpoint with strict owner verification returning 404 for non-owners. |
| 13 | **Is usage idempotent and reconcilable?** | `TryOnUsage` recorded aggregate usage without user/job IDs (privacy-preserving). | Retain anonymous `TryOnUsage` for telemetry; use `TryOnProviderAttempt` for audited provider-job reconciliation. |
| 14 | **Are stale jobs and orphan objects recovered?** | `claim_next_job` handled expired leases; S3 orphan cleanup was not formalized. | Formalize recovery worker logic for expired leases, ambiguous submissions, and S3 cleanup. |

## 4. Audit Conclusion
The repository possesses strong foundations in `TryOnJob`, `TryOnArtifact`, `TryOnUsage`, `ProcessTryOnJobUseCase`, `FashnApiAdapter`, and `S3Storage`. Implementing Phase 07.4 requires extending these existing components into an integrated, fail-closed, and recoverable state machine rather than building a separate subsystem.
