# Phase 07.4.08 — Provider Submission and Attempt Tracking

## 1. Overview
The point of provider submission is the boundary where external financial costs and third-party data processing commence. Blind retries, unrecorded attempts, or premature timeouts can lead to double billing and orphaned provider tasks.

Phase 07.4 introduces durable **Provider Attempt Pre-Persistence** and strict **Ambiguous Submission Handling**.

---

## 2. Provider Attempt Pre-Persistence

Before any HTTP request leaves the FashXStudio backend towards FASHN or another provider, a row in `tryon_provider_attempts` is created and committed:

```python
attempt = TryOnProviderAttempt(
    id=uuid4(),
    job_id=job.id,
    attempt_number=attempt_num,
    provider=self.adapter.provider_name,
    status=ProviderAttemptStatus.SUBMITTING,
    started_at=utcnow(),
)
await self.tryon_uow.provider_attempts.create(attempt)
await self.tryon_uow.commit()
```

### Why Pre-Persistence Matters
If the worker crashes or is abruptly killed immediately after sending the POST request:
- On restart, the worker detects an existing attempt with status `SUBMITTING`.
- The worker will **not** dispatch a second POST.
- Instead, it checks whether the provider processed the request using the attempt's correlation ID or reconciliation query.

---

## 3. Ambiguous Submission Handling (`SUBMISSION_UNKNOWN`)

Network failures during HTTP POST can occur in three distinct phases:
1. **Connect Timeout**: Request never reached provider. Safe to retry.
2. **Read Timeout**: Provider received the payload and is processing, but HTTP response timed out or TCP connection dropped.
3. **502/503/504 Bad Gateway**: Upstream proxy failed; provider backend state unknown.

### Handling Rule
In case of a read timeout, connection reset, or transient 5xx during submission POST:
1. Worker updates `TryOnProviderAttempt.status = "UNKNOWN"`.
2. Worker transitions `TryOnJob.status = "SUBMISSION_UNKNOWN"`.
3. Worker **halts further submission attempts** for this job.
4. Alerts the operations team and queues the job for the reconciliation worker.
5. **Never blind re-submit**: Blindly submitting again could generate two parallel inferences, incurring double billing and delivering conflicting artifacts.
