# Phase 07.4.02 — Job State Machine and Transition Rules

## 1. Overview
The Virtual Try-On (VTO) state machine governs the lifecycle of every try-on job in FashXStudio from request acceptance to terminal outcome. The primary source of truth is PostgreSQL (`tryon_jobs.status`), guaranteeing that queue deliveries, worker restarts, and external provider latencies cannot introduce illegal jumps, stale overwrites, or double execution.

---

## 2. Status Definitions

The state machine defines 10 discrete statuses partitioned into **Active/Transient**, **Intermediate**, and **Terminal** sets:

| Status | Category | Meaning | Retryable? |
| :--- | :--- | :--- | :--- |
| `QUEUED` | Active | Job accepted and persisted; transactional outbox event written. Awaiting worker claim. | Yes (Worker claim) |
| `PROCESSING` | Active | Claimed by worker with an active lease (`locked_by`, `lock_expires_at`). Performing authorization and validation re-checks. | Yes (On lease expiration) |
| `SUBMITTED` | Active | Confirmed submitted to external provider; `provider_job_id` and `TryOnProviderAttempt` recorded. Awaiting polling or webhook completion. | Yes (Polling recovery) |
| `SUBMISSION_UNKNOWN` | Intermediate | Provider submission POST timed out or network severed before HTTP response. Ambiguous whether provider accepted or charged. | No (Requires reconciliation) |
| `COMPLETED` | Terminal | Provider inference succeeded, output bytes downloaded, SSRF verified, Pillow-decoded, private S3 stored, and artifact committed. | No (Immutable terminal) |
| `FAILED` | Terminal | Deterministic or unrecoverable error (e.g. invalid bytes, provider permanent error, retries exhausted). Error code recorded. | No (Immutable terminal) |
| `PERMISSION_BLOCKED` | Terminal | Shopper revoked DPDP consent or merchant takedown occurred during worker time-of-use recheck. | No (Immutable terminal) |
| `VALIDATION_FAILED` | Terminal | Phase 07.3 input validation failed during worker pre-inference execution. | No (Immutable terminal) |
| `QUALITY_REJECTED` | Terminal | Provider returned an image that failed post-inference visual assessment (e.g. blank canvas, severe artifacts). | No (Immutable terminal) |
| `CANCELLED` | Terminal | Shopper or administrative cancellation prior to provider dispatch. | No (Immutable terminal) |

## 3. Transition Matrix

Every transition is strictly validated against `LEGAL_TRANSITIONS` in `backend/fashx/tryon/domain/state_machine.py`. Any attempt to perform an unlisted jump raises `InvalidJobTransitionError`:

```
                 +-----------+
                 |  QUEUED   |
                 +-----+-----+
                       | (Worker claim)
                       v
                 +-----------+
        +------->| PROCESSING|<---------+
        |        +-----+-----+          |
        |              | (Submit POST)  |
        |              +----------------+ (Lease expiry recovery)
        |              |
        |      +-------+-------+
        |      |               |
        |      v               v
  (Reconcile) +-----------+   +--------------------+
        +-----| SUBMITTED |   | SUBMISSION_UNKNOWN |
              +-----+-----+   +---------+----------+
                    |                   |
                    | (Poll / Complete) | (Reconciliation)
                    v                   v
            [ Terminal States ] <-------+
            - COMPLETED
            - FAILED
            - PERMISSION_BLOCKED
            - VALIDATION_FAILED
            - QUALITY_REJECTED
            - CANCELLED
```

### Transition Table

| Source Status | Allowed Target Statuses | Trigger / Conditions |
| :--- | :--- | :--- |
| `QUEUED` | `PROCESSING`, `CANCELLED` | Worker claims job via `claim_next_job`, or shopper cancels before pickup. |
| `PROCESSING` | `SUBMITTED`, `SUBMISSION_UNKNOWN`, `PERMISSION_BLOCKED`, `VALIDATION_FAILED`, `FAILED`, `CANCELLED`, `QUEUED` | Provider submission success (`SUBMITTED`), network timeout (`SUBMISSION_UNKNOWN`), consent/takedown (`PERMISSION_BLOCKED`), validation fail (`VALIDATION_FAILED`), retryable lease surrender (`QUEUED`), or worker fatal error (`FAILED`). |
| `SUBMITTED` | `COMPLETED`, `QUALITY_REJECTED`, `FAILED`, `CANCELLED` | Polling retrieved output and passed validation (`COMPLETED`), output visual check failed (`QUALITY_REJECTED`), provider reported failed inference or timeout (`FAILED`). |
| `SUBMISSION_UNKNOWN` | `SUBMITTED`, `FAILED`, `PROCESSING` | Reconciliation worker queries provider by idempotency key/reference: if provider processed $\rightarrow$ `SUBMITTED`; if provider has no record $\rightarrow$ `PROCESSING` (re-submit) or `FAILED`. |
| `COMPLETED` | *(None)* | **Terminal**. Any transition raises `InvalidJobTransitionError`. |
| `FAILED` | *(None)* | **Terminal**. Any transition raises `InvalidJobTransitionError`. |
| `PERMISSION_BLOCKED`| *(None)* | **Terminal**. Any transition raises `InvalidJobTransitionError`. |
| `VALIDATION_FAILED` | *(None)* | **Terminal**. Any transition raises `InvalidJobTransitionError`. |
| `QUALITY_REJECTED`  | *(None)* | **Terminal**. Any transition raises `InvalidJobTransitionError`. |
| `CANCELLED`         | *(None)* | **Terminal**. Any transition raises `InvalidJobTransitionError`. |

## 4. Lease Ownership & Conditional Transitions

To prevent zombie or stale workers from overwriting database records, all updates while in `PROCESSING` must be executed conditionally using `transition_if_owned`:

```python
job = await self.tryon_uow.jobs.transition_if_owned(
    job_id=job.id,
    expected_status=JobStatus.PROCESSING,
    new_status=JobStatus.SUBMITTED,
    worker_id=self.worker_id,
    progress_stage=ProgressStage.SUBMITTED,
    provider_job_id=provider_job_id,
    provider_submitted_at=utcnow(),
)
```

The underlying SQL executes an atomic conditional update:
```sql
UPDATE tryon_jobs
SET status = :new_status,
    progress_stage = :progress_stage,
    provider_job_id = :provider_job_id,
    provider_submitted_at = :provider_submitted_at,
    updated_at = :now
WHERE id = :job_id
  AND status = :expected_status
  AND locked_by = :worker_id
  AND lock_expires_at > :now;
```
If 0 rows are updated, `TryOnConcurrencyError` is raised, stopping the worker immediately.

## 5. Granular Progress Stages

In addition to `status`, the client and mobile app observe `progress_stage` (persisted in `tryon_jobs.progress_stage`) for transparent UX without exposing internal error logs:
1. `QUEUED`: Job is waiting in queue.
2. `VALIDATING_INPUTS`: Performing image decoding, category policy check, and visual assessment.
3. `RECHECKING_PERMISSIONS`: Checking time-of-use DPDP consent and merchant rights.
4. `PREPARING_INFERENCE`: Constructing normalized RGB JPEGs and signed access URLs.
5. `SUBMITTING`: Dispatching POST payload to external provider.
6. `SUBMITTED`: Awaiting provider GPU execution.
7. `GENERATING`: Provider reports inference running.
8. `DOWNLOADING_OUTPUT`: Fetching provider image stream over secure HTTPS.
9. `VALIDATING_OUTPUT`: Inspecting dimensions, Pillow decoding, and visual quality guard.
10. `STORING_RESULT`: Writing private normalized JPEG to S3 bucket.
11. `COMPLETED`: Result ready for authenticated owner access.
