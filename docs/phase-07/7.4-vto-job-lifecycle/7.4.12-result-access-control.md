# Phase 07.4.12 — Result Access Control and Anti-Enumeration

## 1. Overview
Access to generated Virtual Try-On images must be restricted solely to the authenticated shopper who requested the generation. Unauthorized third parties, other authenticated shoppers, and web scrapers must be completely blocked from accessing result images or enumerating valid job IDs.

---

## 2. Anti-Enumeration and Owner Isolation

When a client queries the result endpoint:
- **Endpoint**: `GET /api/v1/tryon/jobs/{job_id}/result`
- **Authentication**: JWT Bearer token required.

### Authorization Gate
The endpoint enforces strict ownership comparison:
```python
if job is None or job.user_id != principal.user_id:
    raise ApiError(status=404, code="job_not_found", message="Job not found")
```

### Why 404 Instead of 403?
If FashXStudio returned `403 Forbidden` for a job ID that exists but belongs to someone else, an attacker could iterate UUIDs or timestamps to probe for the existence of specific jobs (enumeration attack). Returning `404 Not Found` reveals nothing about whether the job exists or not.

---

## 3. Short-Lived Presigned URLs

FashXStudio never proxies image binaries directly through FastAPI application workers. Direct streaming wastes application worker threads and CPU memory.

Instead, the API generates a **short-lived, expiring Amazon S3 presigned URL**:
- **TTL**: 300 seconds (5 minutes).
- **HTTP Method**: Restrictively presigned for `GET` only.
- **Client Cache Control**: `Cache-Control: private, max-age=300`.

After 300 seconds, the presigned signature expires. Mobile apps needing to re-render the image must request a fresh presigned URL from the API, ensuring revoked permissions or deleted accounts take immediate effect.
