# Phase 07.2 — VTO Live Provider Operations and Triage Runbook

## 1. System Role and Scope

This runbook guides on-call engineers, operators, and platform developers in operating, triaging, and maintaining the hosted Virtual Try-On (VTO) integration with FASHN.

---

## 2. Pre-Flight Health Probing

The backend provides a pre-flight connectivity and balance probe in `backend/fashx/infrastructure/tryon/fashn_health.py`:

```python
from fashx.core.dependencies import get_tryon_adapter

adapter = get_tryon_adapter()
if hasattr(adapter, "check_health"):
    report = adapter.check_health()
    print(f"Status: {report.status}, Balance: {report.credits_remaining}, Latency: {report.latency_ms}ms")
```

### Health Status Definitions:
- `HEALTHY`: Endpoint accessible, API key accepted, credits balance > 0.
- `DEGRADED`: Endpoint responsive, but balance is 0 or 402 Payment Required returned.
- `UNHEALTHY`: 401/403 Authentication failed (revoked or misconfigured API key).
- `UNAVAILABLE`: Network unreachable or DNS failure.

## 3. Incident Triage Procedures

### Scenario A: Authentication Failure (`VTOProviderAuthFailure > 0`)
**Symptoms**:
- CloudWatch alarm `VTOProviderAuthAlert` fires.
- Workers fail jobs with `error_code: provider_auth`.
- Health check returns `UNHEALTHY`.

**Remediation**:
1. Confirm provider account status at `https://app.fashn.ai/billing`.
2. Generate or verify the active API key in the FASHN dashboard.
3. Update AWS Secrets Manager secret `/fashx/{env}/tryon/fashn-api-key`:
   ```bash
   aws secretsmanager put-secret-value \
     --region ap-south-1 \
     --secret-id /fashx/{env}/tryon/fashn-api-key \
     --secret-string '{"api_key": "YOUR_NEW_KEY"}'
   ```
4. Perform rolling restart of the try-on worker tasks to ingest new secrets:
   ```bash
   aws ecs update-service \
     --cluster fashx-{env} \
     --service tryon-worker \
     --force-new-deployment
   ```
5. Re-run health probe to verify resolution.

---

### Scenario B: Vendor Credit Depletion (`provider_credits` / HTTP 402)
**Symptoms**:
- Jobs fail with `provider_credits` ("Try-on is temporarily unavailable").
- Health check returns `DEGRADED` with `credits_remaining: 0`.

**Remediation**:
1. Log in to the vendor portal and purchase credits or approve billing renewal.
2. If the budget cap has been reached unexpectedly, inspect `tryon_usage` table to identify recent volume spikes:
   ```sql
   SELECT date_trunc('hour', created_at) AS hr, count(*), sum(cost_usd_est)
   FROM tryon_usage
   WHERE created_at >= NOW() - INTERVAL '24 hours'
   GROUP BY 1 ORDER BY 1 DESC;
   ```
3. Once credits are topped up, provider status returns to `HEALTHY`. Failed jobs with `attempts < 3` will be re-attempted automatically if configured.

---

### Scenario C: Rate Limiting & Concurrency Throttling (`VTOProviderRateLimit > 0` / HTTP 429)
**Symptoms**:
- Spikes in `VTOProviderRateLimit` metric.
- Worker log shows `tryon.provider.submit.error` with `429: rate limited`.

**Remediation**:
1. Confirm if submission rate exceeded `FASHN_MAX_SUBMISSIONS_PER_MINUTE` (default 10/min) or `FASHN_MAX_CONCURRENT_PREDICTIONS` (default 2 in staging, 4 in prod).
2. If traffic legitimately increased, adjust ECS environment variables:
   - `FASHN_POLL_INTERVAL_SECONDS`: Increase from `3.0` to `4.0` or `5.0`.
   - Contact FASHN support to upgrade account concurrency tier if higher parallel throughput is needed.

---

### Scenario D: Vendor Outage or Degradation
**Symptoms**:
- `VTOJobFailed(Outcome=http_500)` or `VTOJobFailed(Outcome=http_502)` spikes.
- Repeated `VTOProviderTimeout` alarms.

**Remediation**:
1. If the vendor suffers an extended outage, enable maintenance mode on try-on endpoints to protect user experience:
   ```bash
   aws ssm put-parameter \
     --name /fashx/{env}/maintenance_mode \
     --value "true" \
     --type String \
     --overwrite
   ```
2. Notify product operations.
3. Queue incoming user jobs safely until vendor recovery is confirmed.

## 4. Privacy and Log Sanitization Rules

In accordance with DPDP and Rule I06:
1. **Never log raw customer photos, garment images, or base64 strings**.
2. **Never log vendor API keys, authorization headers, or pre-signed URL signatures**.
3. All try-on audit events are emitted through `log_provider_event()` which automatically sanitizes strings, bytearrays, and credential keys before logging.
4. The `tryon_usage` database table stores aggregate execution logs (timestamp, provider, model, latency, cost) with **deliberately zero user identifiers or job keys** to guarantee privacy preservation.
