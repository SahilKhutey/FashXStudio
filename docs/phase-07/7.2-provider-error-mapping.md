# Phase 07.2 — VTO Provider Error Mapping and Resilience Architecture

## 1. Architectural Strategy

The virtual try-on workflow must handle network transients, rate limits, credit depletion, and image processing failures gracefully without corrupting job state or double-billing the user.

To prevent vendor lock-in and domain coupling, vendor error codes are normalized into the domain exception `TryOnError` via `backend/fashx/infrastructure/tryon/fashn_errors.py`.

---

## 2. HTTP Error Normalization Catalog

HTTP errors returned by the FASHN API are mapped as follows:

| HTTP Status | Domain Code | Retryable | User-Facing Message | Operational Action / Metric |
|-------------|-------------|-----------|---------------------|----------------------------|
| `400 Bad Request` | `bad_input` | `False` | "We couldn't use this photo or garment. Try another photo." | Emits `VTOJobFailed(Outcome=http_400)`. Do not retry. |
| `401 Unauthorized` | `provider_auth` | `False` | "Try-on is temporarily unavailable." | Emits `VTOProviderAuthFailure` and `VTOJobFailed(Outcome=http_401)`. P1 alert to engineering. |
| `402 Payment Required` | `provider_credits` | `False` | "Try-on is temporarily unavailable." | Emits `VTOJobFailed(Outcome=http_402)`. P1 alert: vendor credits exhausted. |
| `403 Forbidden` | `provider_auth` | `False` | "Try-on is temporarily unavailable." | Emits `VTOProviderAuthFailure`. Check IAM/API permissions. |
| `429 Too Many Requests`| `provider_unavailable` | `True` | "Try-on is busy. We'll retry shortly." | Emits `VTOProviderRateLimit`. Requeue job with exponential backoff. |
| `500 Internal Error` | `provider_unavailable` | `True` | "Try-on is busy. We'll retry shortly." | Emits `VTOJobFailed(Outcome=http_500)`. Requeue job with backoff. |
| `502 / 503 / 504 Gateway`| `provider_unavailable`| `True` | "Try-on is busy. We'll retry shortly." | Emits `VTOJobFailed`. Gateway glitch; requeue job with backoff. |

## 3. Asynchronous Payload Error Taxonomy

When status polling (`GET /status/{id}`) returns `status: "failed"`, the vendor error payload is parsed and classified:

### A. User Input & Detection Failures (Non-Retryable)
These errors indicate issues with the customer's photo or the merchant's garment image. Retrying with identical inputs will produce identical failures and waste credits:
- `ImageLoadError`: One of the input images was undecodable or unreadable by vendor servers.
- `PoseError` / `NoPersonDetectedError` / `FaceDetectionError`: Shopper photo does not contain a clear human body pose.
- `GarmentDetectionError`: Garment boundaries could not be isolated.
- `UnsupportedImageFormat` / `ImageSizeTooSmall` / `ImageSizeTooLarge`: Input dimensions or formats breached vendor limits.
- **Outcome**: Job marked `failed` with user-friendly remediation prompt.

### B. Content Safety Violations (Non-Retryable)
- `ContentPolicyViolation` / `NSFWDetected` / `SafetyCheckFailed`: Triggered by vendor automated safety moderation.
- **Outcome**: Job marked `failed` with domain code `policy_violation`. Zero retries.

### C. Provider Infrastructure Errors (Retryable)
- `PipelineError` / `ModelTimeout` / `GPUOutOfMemory` / `InternalError` / `ServiceUnavailable`: Transient vendor model or GPU hardware failure.
- **Outcome**: Job marked `provider_unavailable` with `retryable=True`. The worker requeues the job up to `TRYON_MAX_ATTEMPTS` (3) before failing closed.

---

## 4. Two-Phase Safe Retry and Idempotency Policy

1. **Submit Idempotency (`POST /run`)**:
   - `FASHN_SUBMIT_MAX_RETRIES = 0`.
   - If a submission encounters a transport disconnect or network timeout *before receiving a response*, it does **NOT** blindly resubmit `/run`. Blind re-submission risks submitting duplicate jobs and paying twice.
   - The worker records `provider_unreachable` and relies on the state machine to recover or fail safely.
2. **Status Polling Resilience (`GET /status/{id}`)**:
   - Polling queries the idempotent status endpoint.
   - Transient transport errors (socket reset, timeout) during polling are retried up to `FASHN_STATUS_MAX_RETRIES` (default 3) with exponential backoff before the poll is abandoned.
   - If the job was already submitted and has a `provider_job_id`, subsequent worker attempts resume polling via `collect(provider_job_id)` instead of re-submitting.

## 5. Metrics and Observability

Metrics are emitted to CloudWatch under namespace `FashX/VTO` with dimensions `Provider=fashn_api` and `ModelVersion=<model>`:
- `VTOJobSubmitted`: Count of jobs submitted to the vendor.
- `VTOJobSucceeded`: Count of completed try-on inferences.
- `VTOJobFailed`: Count of failed attempts with dimension `Outcome=<reason>`.
- `VTOProviderLatency`: Latency in milliseconds from submission to output download.
- `VTOProviderCostEstimate`: Estimated USD cost recorded per job.
- `VTOProviderCreditsUsed`: Vendor credits consumed per job.
- `VTOProviderRateLimit`: Count of 429 rate limit events.
- `VTOProviderAuthFailure`: Count of 401/403 authentication failures.
