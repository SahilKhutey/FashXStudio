# Phase 07.3 — VTO Input Image Validation: Repository and Integration Audit

## 1. Executive Summary

This audit establishes the baseline of existing FashXStudio components, models, and interfaces before implementing Phase 07.3 ("Validate VTO Input Images"). 

The implementation strictly extends existing authoritative repositories, data models, and services rather than introducing duplicate validation pipelines.

## 3. Detailed Architectural Answers

### 1. Which shopper image asset model is already implemented?
- The primary table for shopper fitting reference photos is `user_photos` (`database/models/identity.py`), tracking `id`, `user_id`, `photo_type`, `storage_key`, `status`, `version`, `content_sha256`, `width`, `height`, `image_format`, `file_size_bytes`, `has_person`, `has_face`, and `ready_for_tryon`.
- `UserMedia` (`database/models/media.py`) tracks uploaded media objects with `purpose in ('PROFILE_PHOTO', 'VTO_PERSONAL_PHOTO')`.
- Both models enforce tenant isolation via `user_id`.

### 2. Where is the authoritative consent service?
- Authoritative consent is stored in `consent_records` (`database/models/identity.py`), with append-only audit tracking in `consent_events`.
- Managed in backend services via `ProfileUnitOfWork.consents` (`has_consent(user_id, data_type)` and `has_active_consent(...)`).

### 3. Does the catalog authorization model enforce required permissions?
- Yes. `database/models/catalog_auth.py` defines `CatalogPermissionCode`:
  - `IMAGE_AI_PROCESS`
  - `VTO_PROCESS`
  - `IMAGE_STORE`
  - `IMAGE_DISPLAY`
  - `DERIVATIVE_CREATE`
  - `DERIVATIVE_STORE`
- Permissions are linked to `catalog_sources` with expiration dates, suspension status, and takedown tracking.

### 4. How are merchant products, offers, and images associated?
- A `MerchantProduct` belongs to a `Merchant` and `CatalogSource`.
- A `CanonicalGarment` references normalized product metadata.
- Images are referenced either through `GarmentImage` (`catalog.py`) or `CatalogImageAsset` (`catalog_image.py`).
- Authoritative validation requires verifying that the requested garment image asset is explicitly registered to the target product ID, preventing cross-product or unpermitted image spoofing.

### 5. Are image versions and hashes already stored?
- Yes:
  - `user_photos.version` and `user_photos.content_sha256`.
  - `catalog_image_assets.original_sha256`, `normalized_sha256`, and `permission_revision`.
  - `tryon_jobs.photo_version` and `tryon_jobs.garment_version`.

### 6. Where does the VTO job transition to provider submission?
- In `backend/fashx/tryon/application/process_job.py` within `ProcessTryOnJobUseCase.execute()`.
- Currently, preprocessing decodes image bytes and rechecks consent, but lacks the formal, multi-stage validation gate (technical inspection, category visibility, pose/occlusion, merchant AI processing permissions, and validation record persistence).
- This is where the mandatory validation gate and time-of-use recheck will be placed.

### 7. What Python, Pydantic, Pillow, and vision dependencies are installed?
- Python: `3.12`
- Pillow: `12.1.1`
- Pydantic: `2.12.5`
- FastAPI: `0.141.1`
- SQLAlchemy: `2.0.51`
- All visual assessment and technical inspection can be built using Pillow and clean, replaceable provider protocols without introducing unapproved dependencies (Rule 7).

### 8. Which existing modules should be extended instead of duplicated?
- Create `backend/fashx/tryon/validation/` holding the modular validators and contracts.
- Persist validation audit records in `tryon_input_validations` and `tryon_input_authorization_snapshots` (`database/models/tryon.py`).
- Update `ProcessTryOnJobUseCase` to execute `CombinedVTOInputValidator` and fail-closed if validation does not pass.
