# Phase 07.3.9 — Security, Privacy, and DPDP Compliance Review

## 1. Overview
The Virtual Try-On validation subsystem processes sensitive personal data (shopper body photographs) and merchant intellectual property (catalog garment imagery). This document reviews the security architecture, privacy controls, and compliance guarantees enforced in Phase 07.3.

---

## 2. Regulatory Compliance (India DPDP Act 2023 & GDPR)

### 2.1 Explicit Purpose-Bound Consent
- **Lawful Basis**: Under the Digital Personal Data Protection (DPDP) Act 2023, processing personal biometric and body imagery requires explicit, informed, and revocable consent.
- **Purpose Specification**: Consent is tracked under the specific purpose tag `THIRD_PARTY_VTO_PROCESSING`.
- **Pre-Submission Enforcement**: Every try-on job admits requests only if an active consent event is verified for the authenticated user.
- **Time-of-Use Recheck**: In the event a shopper withdraws consent while a job is pending in the queue, the worker performs a mandatory recheck immediately before external provider dispatch (`backend/fashx/tryon/application/process_job.py`). If consent was withdrawn, the job is cancelled without provider submission.

### 2.2 Right to Withdraw & Erasure
- Shoppers can withdraw VTO consent at any time from Profile Settings.
- Withdrawal immediately prevents new try-on job creation and causes any in-flight queued jobs to abort at time-of-use.
- Profile fitting photos can be deleted by the shopper, triggering S3 deletion and database tombstoning.

## 3. Threat Modeling & Security Controls

### 3.1 Tenant Isolation & Anti-Enumeration
- **Threat**: An attacker attempts to submit UUIDs belonging to other shoppers to try on clothes against another user's private photo, or probe the system to determine if a specific asset UUID exists.
- **Mitigation**:
  - The repository layer filters queries strictly by `user_id == current_user.id`.
  - When an asset ID does not match the authenticated user, the API responds with a generic `404 Not Found` (`IMAGE_NOT_OWNED_OR_NOT_FOUND`).
  - No differential error messaging or timing discrepancy exists between non-existent assets and assets owned by third parties.

### 3.2 Malicious Payload Neutralization (Image Sanitization)
- **Threat**: An attacker uploads an exploit embedded in image EXIF tags, a polyglot executable disguised as an image, or a decompression bomb (zip bomb / decompression bomb) designed to exhaust server RAM.
- **Mitigation**:
  - `Image.MAX_IMAGE_PIXELS = 20_000_000` prevents decompression bombs.
  - PIL parses and strictly verifies the container format (`JPEG`, `PNG`, `WEBP`).
  - All EXIF metadata (including camera model, serial number, GPS location, and arbitrary string tags) is completely stripped.
  - The image is re-rasterized and re-encoded into a clean baseline JPEG in memory before persistence or transmission.

### 3.3 Integrity & Tamper Detection
- **Threat**: Image tampering in transit between client, storage, and worker.
- **Mitigation**:
  - Cryptographic `original_sha256` is computed upon first receipt.
  - Cryptographic `normalized_sha256` is computed on the sanitized raster.
  - Both digests are persisted in the immutable `tryon_input_validations` table.
  - Prior to external provider submission, the worker re-computes the hash of the payload to verify it matches the normalized hash.

### 3.4 Zero Sensitive Data Logging
- **Threat**: Leakage of shopper images or private S3 pre-signed URLs into application logs, Datadog/CloudWatch, or Sentry error traces.
- **Mitigation**:
  - Raw image bytes and base64 strings are never passed to logging statements.
  - Pre-signed URLs are generated with short lifespans (max 15 minutes) and are excluded from structured log payloads.
  - Log events record only non-sensitive metadata: `job_id`, `asset_id`, `role`, `status`, and `normalized_sha256`.
