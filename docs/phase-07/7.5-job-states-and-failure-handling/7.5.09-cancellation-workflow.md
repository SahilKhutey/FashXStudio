# Phase 07.5.09 — Cancellation Workflow and Race Protection

## 1. Overview
Shoppers may cancel try-on jobs at various stages: while queued, while the provider is computing, or after results have been generated.

The cancellation architecture guarantees:
1. **Security & Anti-Enumeration**: Cancellation requests require JWT authentication; querying another user's job raises `JobNotFoundError` (HTTP 404).
2. **Honesty Regarding Provider Compute**: If the provider lacks an asynchronous cancel API, FashX suppresses the result without falsely claiming provider GPU computation has halted.
3. **Immutability of Terminal Records**: Completed jobs cannot be rewritten to `CANCELLED`.
4. **Race Protection**: Cancellation requests during active inference move to `CANCEL_REQUESTED`, preventing workers from silently overwriting the cancellation intent.

## 2. Cancellation Behavior Across Job States

```
[ Cancellation Request Received (POST /api/v1/tryon/jobs/{id}/cancel) ]
                                |
                                v
               +---------------------------------+
               | Is user authenticated owner?   |
               +----------------+----------------+
                                |
                       +--------+--------+
                       |                 |
                     (Yes)              (No)
                       |                 |
                       v                 v
          +-----------------------+   [ HTTP 404 Not Found ]
          | Check Current Status  |
          +-----------+-----------+
                      |
     +----------------+-------------------+----------------+
     |                                    |                |
(QUEUED, RETRY_PENDING, CREATED)    (PROCESSING, SUBMITTED) (COMPLETED, FAILED)
     |                                    |                |
     v                                    v                v
[ Transition to CANCELLED ]    [ Transition to CANCEL_REQUESTED ] [ Reject: HTTP 409 ]
(Immediate safe stop)          (Call provider cancel if available; (No state rewrite)
                                discard generated result)
```

| State When Cancel Arrives | Target State | Immediate? | Provider Action |
| :--- | :--- | :---: | :--- |
| `CREATED` | `CANCELLED` | Yes | Validation stopped. |
| `VALIDATING` | `CANCELLED` | Yes | Pre-inference assessment halted. |
| `QUEUED` | `CANCELLED` | Yes | Dispatch invalidated. |
| `RETRY_PENDING` | `CANCELLED` | Yes | Scheduled retry cancelled. |
| `PROCESSING` (pre-submit) | `CANCELLED` | Yes | Worker aborts before POST. |
| `PROCESSING` (post-submit)| `CANCEL_REQUESTED` | No | Calls provider cancel API if supported; output discarded. |
| `SUBMISSION_UNKNOWN` | `CANCEL_REQUESTED` | No | Reconciled before declaring cancellation final. |
| `OUTPUT_VALIDATING` | `CANCEL_REQUESTED` | No | Download stopped; temporary buffer dropped. |
| `STORING_RESULT` | `CANCEL_REQUESTED` | No | S3 write rolled back or artifact suppressed. |
| `COMPLETED` | *(Conflict)* | No | Raises `CancellationConflictError`; historical record preserved. |
| `CANCELLED` | `CANCELLED` | Yes | Idempotent HTTP 200 response. |

## 3. Cancellation Race Protection Invariant
Consider:
1. Worker submits inference payload to provider.
2. Shopper issues cancellation request $\rightarrow$ job status becomes `CANCEL_REQUESTED`.
3. Provider finishes inference and returns output URL to worker.

### Enforced Protection
When the worker receives output, it must check `job.status`:
- If `status == CANCEL_REQUESTED`, the worker **must not** transition the job to `COMPLETED`.
- The worker drops the output image without saving an artifact.
- The worker completes the cancellation transition to `CANCELLED`.
