# Phase 07.5.05 — Error Taxonomy and Operational Classification

## 1. Overview
Automated retry loops without explicit error classification cause severe operational failure:
- Retrying permanent errors (e.g. invalid photo) wastes worker capacity and delays customer feedback.
- Retrying configuration errors (e.g. invalid API key) causes repeated provider 401s without resolution.
- Retrying ambiguous timeouts blindly causes duplicate inference charges.

FashXStudio implements a comprehensive taxonomy in `backend/fashx/tryon/lifecycle/errors.py`.

---

## 2. Error Categories (`ErrorCategory`)

| Category | Automated Retry? | Meaning & Strategy |
| :--- | :---: | :--- |
| `TRANSIENT` | **Yes (Bounded)** | Short-lived network or resource hiccups (e.g. 503, connection reset). Retry with exponential backoff and jitter. |
| `PERMANENT` | **No** | Input data or business rule failure (e.g. invalid photo, missing consent). Terminate immediately and provide user guidance. |
| `CONFIGURATION` | **No** | Operator error (e.g. invalid credentials, credit exhaustion). Halt submissions and trigger high-priority alerts. |
| `AMBIGUOUS` | **No (Manual/Reconcile)**| Outcome cannot be verified (e.g. POST timeout). Transition to `SUBMISSION_UNKNOWN` and reconcile; never blind re-post. |
| `CANCELLED` | **No** | User or system cancelled job. |

## 4. Fail-Closed Invariant on Unknown Errors
If an unexpected exception occurs or an unmapped string is received, `classify_error()` defaults strictly to:
- `category = ErrorCategory.PERMANENT`
- `retryable = False`
- `safe_to_repeat = False`
This ensures unhandled errors never spin in infinite, costly retry loops.
