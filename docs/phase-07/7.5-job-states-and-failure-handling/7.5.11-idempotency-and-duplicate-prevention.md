# Phase 07.5.11 — Comprehensive Duplicate Prevention and Financial Protection

## 1. Overview
Virtual Try-On is vulnerable to four distinct duplicate execution vectors across the distributed stack. Solving only one layer leaves the application exposed to redundant GPU charges, conflicting images, or client race conditions.

---

## 2. Four Duplicate Vectors & Mitigations

| Duplicate Vector | Example Failure Scenario | Protection Mechanism |
| :--- | :--- | :--- |
| **1. Duplicate API Request** | Shopper rapidly taps "Try On" twice on mobile app. | `Idempotency-Key` + canonical `request_hash` lookup. Same payload $\rightarrow$ returns existing job; conflicting payload $\rightarrow$ HTTP 409 Conflict. |
| **2. Duplicate Queue Delivery** | Celery / Redis redelivers task due to network ACK timeout. | Atomic worker claim using compare-and-set on `(status, lease_expires_at)`. Second worker fails claim and exits. |
| **3. Duplicate Provider Submission**| POST to provider times out; worker retries blind POST. | `TryOnProviderAttempt` pre-persistence. Network timeout transitions to `SUBMISSION_UNKNOWN`. Requires reconciliation; automatic re-post is blocked. |
| **4. Duplicate Result Artifact**| Worker uploads image and attempts duplicate artifact commit.| Unique database constraint `uq_tryon_artifact_job` and deterministic S3 key `tryon-results/{job_id}.jpg`. |

---

## 3. Financial Invariant: Zero Duplicate Inferences
Under no circumstance will an automated retry dispatch a second HTTP POST to an external provider if the first POST may have reached the provider's GPU cluster.

All ambiguous outcomes route through the reconciliation path:
$$\text{HTTP Connect / Read Timeout} \longrightarrow \texttt{SUBMISSION\_UNKNOWN} \longrightarrow \text{Query Provider by Reference} \longrightarrow \text{Reconcile / Alert}$$
