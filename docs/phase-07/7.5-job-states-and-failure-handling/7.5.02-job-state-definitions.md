# Phase 07.5.02 — Job State Definitions and Attempt Separation

## 1. Overview
Virtual Try-On (VTO) execution is an asynchronous, multi-stage workflow involving shopper consent checks, merchant permissions, external GPU inference, secure image downloads, format hardening, and private object storage.

To prevent duplicate inference charges and race conditions, FashXStudio strictly separates **Durable Job States** from **Provider Attempt States**.

---

## 2. Authoritative Job States (`JobStatus`)

The lifecycle defines 13 discrete job states partitioned into Active, Intermediate, and Terminal categories:

| State | Category | Meaning | Terminal? | Retryable? | Entry Condition | Exit Condition |
| :--- | :--- | :--- | :---: | :---: | :--- | :--- |
| `CREATED` | Active | Initial job record persisted in database. | No | Yes | API receives try-on request and commits row. | Moves to `VALIDATING` or `CANCELLED`. |
| `VALIDATING` | Active | Pre-inference shopper and merchant validation checks running. | No | Yes | Transition from `CREATED`. | Input passes $\rightarrow$ `QUEUED`; fails $\rightarrow$ `FAILED`. |
| `QUEUED` | Active | Validation passed; outbox event enqueued; awaiting worker pickup. | No | Yes | Validation pass or safe worker recovery. | Worker claims job $\rightarrow$ `PROCESSING`. |
| `PROCESSING` | Active | Worker holds an active lease and is actively executing/polling. | No | Yes | Worker acquires lease via compare-and-set. | Moves to `OUTPUT_VALIDATING`, `SUBMISSION_UNKNOWN`, `RETRY_PENDING`, or `FAILED`. |
| `SUBMISSION_UNKNOWN` | Intermediate | Provider submission POST timed out or network severed before HTTP response. | No | No (Auto) | Connection failure during outbound POST to provider. | Reconciliation confirms provider state $\rightarrow$ `PROCESSING`, `RETRY_PENDING`, or `FAILED`. |
| `RETRY_PENDING` | Intermediate | Safe transient failure occurred; backoff delay active. | No | Yes | Retryable error classified with retries remaining. | Sweeper or scheduler picks up job $\rightarrow$ `PROCESSING`. |
| `OUTPUT_VALIDATING` | Active | Provider returned output URL; image bytes being downloaded and hardened. | No | Yes | Provider status indicates completion. | SSRF and Pillow decode pass $\rightarrow$ `STORING_RESULT`; fail $\rightarrow$ `FAILED`. |
| `STORING_RESULT` | Active | Validated image bytes being written to private S3 storage. | No | Yes | Image validation succeeded. | HeadObject verify pass $\rightarrow$ `COMPLETED`; fail $\rightarrow$ `FAILED`. |
| `CANCEL_REQUESTED` | Intermediate | Shopper requested cancellation while inference is in flight. | No | No | Shopper invokes `POST /jobs/{id}/cancel` while active. | Safe worker teardown confirmed $\rightarrow$ `CANCELLED`. |
| `COMPLETED` | Terminal | Generated image securely stored in S3 and artifact committed. | Yes | No | S3 write verified and DB transaction committed. | Expiry date reached $\rightarrow$ `EXPIRED`. |
| `FAILED` | Terminal | Permanent error, unrecoverable failure, or retries exhausted. | Yes | No | Non-retryable error or retry count $\ge$ max. | None (Immutable terminal). |
| `CANCELLED` | Terminal | Job cancelled safely prior to result publication. | Yes | No | Cancellation confirmed. | None (Immutable terminal). |
| `EXPIRED` | Terminal | Result pruned according to DPDP 30-day retention policy. | Yes | No | Lifecycle sweeper prunes image after retention window. | None (Immutable terminal). |

## 3. Provider Attempt States (`ProviderAttemptStatus`)

A job may have one or more provider attempts recorded in `tryon_provider_attempts`. Overloading job states with provider events causes confusion when transient provider network errors occur.

Attempt states:
1. `PREPARED`: Request payload and signed input assets constructed.
2. `SUBMITTING`: Attempt persisted and outbound HTTP POST initiated.
3. `ACCEPTED`: HTTP 200/202 received from provider; `provider_job_id` recorded.
4. `UNKNOWN`: Network timed out during POST; outcome unconfirmed.
5. `POLLING`: Status checks active against provider API.
6. `SUCCEEDED`: Provider returned successful inference status.
7. `FAILED`: Provider reported failure (e.g. content policy, internal error).
8. `ABANDONED`: Attempt abandoned during recovery without incurring duplicate inference.
