# Phase 07.5.17 — Operational Reliability and Incident Runbook

## 1. Overview
This runbook guides on-call engineers in triaging and resolving Virtual Try-On failures, investigating dead-letter records, reconciling ambiguous provider submissions, and clearing worker lease contention.

---

## 2. Playbooks for Common Incidents

### Playbook 1: Triaging `tryon_dead_letters` Backlog
- **Alert**: `vto_dead_letters_open > 5`
- **Triage Steps**:
  1. Inspect open dead letters:
     ```sql
     SELECT id, job_id, source, failure_stage, error_code, error_summary, created_at
     FROM tryon_dead_letters
     WHERE status = 'OPEN'
     ORDER BY created_at DESC;
     ```
  2. For `PROVIDER_AUTH_FAILED`: Verify secret in AWS Secrets Manager (`/fashx/staging/tryon/fashn-api-key`). Rotate or update API key.
  3. For `MAX_RETRIES_EXCEEDED`: Check if downstream S3 or provider had an outage that has since recovered.
  4. To replay safe jobs:
     ```python
     await dlq_service.replay_dead_letter(dlq_id, operator_id="engineer", note="S3 outage cleared")
     ```

---

### Playbook 2: Reconciling `SUBMISSION_UNKNOWN` Jobs
- **Alert**: `vto_provider_submission_unknown > 0`
- **Rule**: **Never run a manual retry that calls POST again without checking provider logs.**
- **Triage Steps**:
  1. Check attempt record:
     ```sql
     SELECT id, job_id, provider, request_hash, status, started_at
     FROM tryon_provider_attempts
     WHERE status = 'UNKNOWN';
     ```
  2. Query provider API or dashboard using `request_hash` / client reference ID.
  3. If provider processed job:
     - Update attempt status to `ACCEPTED` with `provider_job_id`.
     - Transition job to `PROCESSING` to resume polling.
  4. If provider has no record:
     - Mark attempt `ABANDONED`.
     - Transition job to `QUEUED` for safe re-attempt or `FAILED`.

---

### Playbook 3: Stuck Worker Leases (`PROCESSING`)
- **Alert**: `vto_worker_lease_expired_total spike`
- **Triage Steps**:
  1. Check jobs with expired leases:
     ```sql
     SELECT id, status, worker_id, lease_expires_at, heartbeat_at, version
     FROM tryon_jobs
     WHERE status = 'PROCESSING' AND lease_expires_at < NOW();
     ```
  2. Run stuck job sweeper:
     ```bash
     python -m fashx.tryon.lifecycle.recovery --recover-expired-leases
     ```
  3. The sweeper resets expired jobs to `QUEUED` without losing progress.
