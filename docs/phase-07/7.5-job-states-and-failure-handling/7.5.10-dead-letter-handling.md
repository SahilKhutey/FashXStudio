# Phase 07.5.10 — Dead-Letter Handling and Investigation Procedures

## 1. Overview
When a Virtual Try-On job fails unrecoverably or exhausts its permitted retry budget, it must not disappear or cause endless reprocessing.

FashXStudio provides a dedicated, durable **Dead-Letter Queue (DLQ)** table in PostgreSQL (`tryon_dead_letters`), managed by `DeadLetterService`.

---

## 2. Dead-Letter Schema (`tryon_dead_letters`)

```sql
CREATE TABLE tryon_dead_letters (
    id UUID PRIMARY KEY,
    job_id UUID NULL REFERENCES tryon_jobs(id) ON DELETE SET NULL,
    source VARCHAR(100) NOT NULL,
    failure_stage VARCHAR(50) NOT NULL,
    error_code VARCHAR(64) NOT NULL,
    error_summary VARCHAR(500) NOT NULL,
    attempt_number INTEGER NOT NULL DEFAULT 0,
    original_message_id VARCHAR(255) NULL,
    payload_reference JSONB NOT NULL DEFAULT '{}'::jsonb,
    status VARCHAR(32) NOT NULL DEFAULT 'OPEN',
    resolution_note TEXT NULL,
    resolved_by VARCHAR(100) NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    resolved_at TIMESTAMPTZ NULL,
    CONSTRAINT ck_tryon_dlq_status
      CHECK (status IN ('OPEN', 'INVESTIGATING', 'REPLAYED', 'DISCARDED', 'RESOLVED')),
    CONSTRAINT ck_tryon_dlq_attempt_nonnegative
      CHECK (attempt_number >= 0)
);
```

---

## 3. Privacy & Sanitization Invariant

`payload_reference` contains diagnostic context needed for operational debugging. In accordance with DPDP and security standards:
- **Forbidden Substrings / Keys Scrubbed**:
  - `authorization` headers / bearer tokens
  - `api_key` or provider secrets
  - raw image bytes or base64 rasters
  - presigned S3 URLs
- Only non-PII operational identifiers (`job_id`, `category`, `error_code`, `attempts`) are persisted.

---

## 4. Controlled Replay Procedure

Dead letters cannot be blindly re-executed:
1. **Operator Investigation**: Engineer sets status to `INVESTIGATING` and reviews error logs.
2. **Safety Check**:
   - Verify whether the external provider accepted or billed the inference request.
   - If the provider already completed inference, replay consists of re-fetching the output or re-running storage persistence, **never dispatching a second paid POST**.
3. **Controlled Replay**:
   ```python
   await dead_letter_service.replay_dead_letter(
       dead_letter_id=dlq.id,
       operator_id="eng-bob",
       note="Verified provider billed attempt 1; safe to re-download output",
   )
   ```
4. **Resolution**: Marked `REPLAYED` or `DISCARDED` with timestamp and operator identity.
