# Phase 07.5.12 — Worker Restart Recovery and Checkpoint Resumption

## 1. Overview
Worker pod recycling, node updates, and autoscaling events must not cause in-flight Virtual Try-On jobs to fail or re-run completed steps.

FashXStudio workers implement **Checkpoint Resumption**: on restart, a worker inspects durable PostgreSQL state and resumes from the exact stage reached before the interruption.

---

## 2. Checkpoint Resumption Rules

```
[ Worker Restarts & Claims Job ]
                |
                v
  [ Inspect Durable Database Checkpoint ]
                |
    +-----------+-----------+--------------------+
    |                       |                    |
(No Provider ID)   (Provider ID Saved)  (Output Bytes Validated)
    |                       |                    |
    v                       v                    v
[ Submit to Provider ] [ Resume Polling ] [ Resume Private S3 PUT ]
(Fresh attempt)        (Skip inference)   (Skip inference & download)
```

| Checkpoint State in DB | Resumption Action | Invariant |
| :--- | :--- | :--- |
| `QUEUED` / `RETRY_PENDING` | Begin pre-inference checks and submission. | Acquires new worker lease. |
| `PROCESSING`, `provider_job_id` is `None` | Safe to execute fresh provider submission. | Records attempt 1. |
| `PROCESSING`, `provider_job_id` exists | **Skip submission**; resume status polling immediately. | No second POST. |
| `PROCESSING`, output downloaded | **Skip polling**; proceed directly to image validation & S3 upload.| Reuses in-memory or cached stream. |
| `STORING_RESULT`, object exists in S3 | Verify object via `HeadObject`; commit `COMPLETED`. | No duplicate upload. |

---

## 3. Durable Outbox Relay Invariant
Even if the Celery message broker (Redis / RabbitMQ) suffers an outage:
1. `TryOnJob` and `OutboxMessageRecord` (`outbox_messages`) are committed atomically in PostgreSQL.
2. The outbox relay automatically detects unpublished events and redelivers them once the broker reconnects.
3. No jobs are lost during message broker downtime.
