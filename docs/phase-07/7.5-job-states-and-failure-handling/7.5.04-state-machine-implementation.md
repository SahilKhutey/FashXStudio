# Phase 07.5.04 — State Machine Implementation and Concurrency Defense

## 1. Overview
Application-level Python transition checks are insufficient on their own to prevent race conditions when multiple background workers or API processes act on the same job.

FashXStudio combines:
1. **Python Domain State Machine**: Strict transition validation via `validate_transition()`.
2. **Database Compare-and-Set (CAS)**: Atomic conditional SQL updates on `(id, status, version, worker_id)`.
3. **Optimistic Versioning**: Incrementing integer `version` preventing lost updates.
4. **Append-Only Event Ledger**: Writing to `tryon_job_events` in the same transaction.

---

## 2. Python State Machine Architecture

Defined in `backend/fashx/tryon/lifecycle/`:
- `states.py`: Canonical `JobStatus` and `ProviderAttemptStatus` enums.
- `transitions.py`: `ALLOWED_TRANSITIONS` map and `validate_transition` validator.
- `service.py`: `JobLifecycleService` orchestrating transitions and optimistic concurrency.

```python
curr_enum, target_enum = validate_transition(expected_status, target_status)
```

## 3. Atomic Database Compare-and-Set Pattern

In `TryOnJobRepository.transition_with_version_and_event`:

```sql
UPDATE tryon_jobs
SET status = :target_status,
    version = tryon_jobs.version + 1,
    updated_at = :now
WHERE tryon_jobs.id = :job_id
  AND tryon_jobs.status = :expected_status
  AND tryon_jobs.version = :expected_version
  AND (tryon_jobs.worker_id = :worker_id OR tryon_jobs.locked_by = :worker_id);
```

### Race Resolution
- If Worker A and Worker B both read `version = 2` and attempt to transition the job:
  - Worker A's update executes first, updating `status` and setting `version = 3`.
  - Worker B's SQL statement matches 0 rows because `version == 2` is no longer true.
  - Worker B receives `False` from the database and raises `StaleVersionError`, rolling back its transaction cleanly without corrupting the job.

## 4. Append-Only Transition Event Logging

Within the same database transaction:
```python
event = TryOnJobEvent(
    id=uuid4(),
    job_id=job_id,
    from_state=expected_status,
    to_state=target_status,
    event_type="JOB_STATE_TRANSITION",
    reason_code=reason_code,
    actor_type=actor_type,
    worker_id=worker_id,
    metadata_json=metadata or {},
    created_at=now_ts,
)
session.add(event)
```
This guarantees an immutable audit trail for every state change in the system.
